# DJI-Market — Sales Performance Dashboard

Full-stack дашборд аналитики продаж менеджеров: ASP.NET Core (.NET 10) + PostgreSQL + React/TypeScript.
Поднимается одной командой, миграции и seed применяются автоматически.

```
DJI-Market/
├─ backend/            ASP.NET Core (.NET 10) + EF Core + PostgreSQL
├─ frontend/           React + TypeScript + Vite
├─ docker-compose.yml  db + api + web
├─ README.md
├─ AI_PROMPTS.md
└─ AI_NOTES.md
```

## Запуск

```bash
git clone https://github.com/OlegSvekla/DJI-Market.git
cd DJI-Market
docker compose up --build
```

Больше ничего делать не нужно: PostgreSQL поднимается, EF Core migrations применяются на старте API,
seed-данные создаются автоматически при пустой базе. Первый запуск дополнительно скачивает
около 1,5 ГБ базовых образов (.NET SDK и runtime, node, nginx, postgres) — дальше они кэшируются.

Проверено полным прогоном с нуля: `docker compose down -v` → `docker compose up --build` →
контейнеры `dji-db` (healthy), `dji-api`, `dji-web`; в логах API видно применение миграций
и seed 3501 продажи; дашборд на `http://localhost:3000` открывается уже заполненным.

После старта:

| Сервис | Адрес |
|---|---|
| Dashboard | http://localhost:3000 |
| API + Swagger | http://localhost:5080/swagger |
| PostgreSQL | localhost:5433 (`dji` / `dji` / `dji_sales`) |

Порты переопределяются через `.env` (см. `.env.example`).

## Локальный запуск без Docker

Строка подключения нигде не коммитится. Для локальной разработки она задаётся через user-secrets:

```bash
docker compose up -d db
dotnet user-secrets set "ConnectionStrings:Postgres" "Host=localhost;Port=5433;Database=dji_sales;Username=dji;Password=<ваш пароль>" --project backend/src/DJI.Web
dotnet run --project backend/src/DJI.Web
```

Альтернатива — переменная окружения `ConnectionStrings__Postgres`. В контейнере используется именно она:
её выставляет `docker-compose.yml`. В `appsettings.json` строки подключения нет вообще.

Фронтенд в dev-режиме:

```bash
cd frontend && npm install && npm run dev
```

## Архитектура

```
backend/
├─ src/
│  ├─ DJI.Core            — базовая сущность и домен, enum'ы, правила расчёта KPI
│  ├─ DJI.Contracts       — DTO запросов/ответов API (публичный контракт)
│  ├─ DJI.Infrastructure  — EF Core: DbContext, конфигурации, миграции, seed, репозиторий
│  ├─ DJI.Bl              — сервисы аналитики, модели расчёта и мапперы в ответы
│  └─ DJI.Web             — ASP.NET Core: контроллеры, DI, обработка ошибок, Swagger
├─ tests/DJI.Tests        — xUnit: расчёт KPI, фильтр периода, рейтинг, статусы продаж
└─ DJI.Market.slnx
```

Frontend отдаётся nginx'ом, который проксирует `/api` на контейнер `api` — фронт ходит по относительным
путям, поэтому CORS в проде не нужен и адрес бэкенда не зашивается в бандл.

## Business rules

| Показатель | Правило |
|---|---|
| Revenue | сумма позиций продаж со статусом `Paid` |
| Gross Profit | `Revenue − Cost`, где Cost — себестоимость позиций тех же продаж |
| Margin | `Gross Profit / Revenue`, при `Revenue = 0` → `null` (не 0) |
| Average Check | `Revenue / количество продаж Paid` |
| Cancelled | не участвует ни в одной денежной метрике |
| Refunded | **исключается** из Revenue/Gross Profit/Average Check и показывается отдельно: сумма возвратов и refund rate |
| Предыдущий период | сдвиг текущего диапазона назад на его собственную длину (`[from − len; from)`), сравнение — в процентах |

Границы диапазона: `from` включительно, `to` включительно по дате (сравнение по `date >= from AND date < to + 1 day`),
чтобы продажа ровно на границе попадала в период ровно один раз.

## API

Все эндпоинты — GET, авторизации нет. Период задаётся одинаково везде:
`preset=Today|Last7Days|Last30Days|ThisMonth|LastMonth|Custom`, для `Custom` — ещё `from` и `to`
в формате `yyyy-MM-dd`. Обе границы включительные.

| Эндпоинт | Параметры | Что отдаёт |
|---|---|---|
| `GET /api/analytics/kpi` | период | выручка, валовая прибыль, маржа, количество продаж, средний чек, возвраты, лучший менеджер — каждый показатель со значением за прошлый период и процентом изменения |
| `GET /api/analytics/managers` | период, `sortBy=GrossProfit\|AverageCheck\|Revenue`, `limit` | рейтинг с позицией, метриками и изменением к прошлому периоду |
| `GET /api/analytics/timeseries` | период, `granularity=Auto\|Day\|Week\|Month` | точки графика выручки, прибыли и количества продаж |
| `GET /api/analytics/categories` | период | выручка, прибыль, маржа и доля каждой категории |
| `GET /api/analytics/top-products` | период, `limit` | лучшие товары по выручке |
| `GET /api/sales/recent` | период, `page`, `pageSize`, `managerId`, `status` | последние продажи с пагинацией |
| `GET /api/meta/filters` | — | менеджеры, категории, статусы и фактические границы истории продаж |
| `GET /health` | — | проверка живости |

Все расчёты и фильтрация — на сервере; фронтенд не тянет сырые продажи.
Доступ к данным — только Entity Framework Core: агрегаты (`GroupBy` + `Sum`) транслируются в SQL,
сущности целиком в память не поднимаются. Raw SQL и Dapper не используются.

### Поведение в пограничных случаях

| Ситуация | Ответ |
|---|---|
| Период без продаж | 200, нули по деньгам, `null` в марже и среднем чеке, пустые списки — не ошибка |
| Пустой прошлый период | значение есть, `changeRate` — `null`: рост «с нуля» в процентах не выражается |
| Продажа ровно на границе диапазона | входит в период ровно один раз, проверено сравнением с прямым SQL |
| Одинаковые результаты у двух менеджеров | общая позиция, следующая пропускается (1, 2, 2, 4) |
| Менеджер без продаж за период | остаётся в рейтинге, но всегда ниже тех, у кого продажи были |
| `from` позже `to`, `Custom` без дат, диапазон больше трёх лет | 400 с описанием проблемы в `application/problem+json` |

## Технические решения

### Слои

`DJI.Web` разбирает запрос и отдаёт ответ, `DJI.Bl` содержит сервис на каждый функционал дашборда,
`DJI.Infrastructure` — доступ к данным, `DJI.Core` — сущности и чистые формулы, `DJI.Contracts` — DTO.
MediatR, UnitOfWork и отдельный слой Application не заводились: команд в системе нет,
все восемь эндпоинтов read-only, и дополнительный слой не решал бы никакой конкретной задачи.

### Репозиторий

Все сущности наследуют `Entity` с единственным полем `Id` — это позволяет ограничить репозиторий
`where TEntity : Entity` и дать ему чтение по идентификатору. Аудитных полей в базовом классе нет:
в рантайме приложение ничего не пишет, кроме seed, и они были бы мёртвым грузом.

`IRepository<TEntity>` — один открытый дженерик на все сущности, без пустых наследников вида
`SaleRepository : Repository<Sale>`. Главное ограничение: у каждого чтения обязателен `selector`,
метода, отдающего сущности целиком, в интерфейсе нет. Поэтому проекция уходит в SQL, а агрегаты
(`GroupBy` + `Sum`) строятся поверх `Query()` и считаются в Postgres — дашборд не поднимает
тысячи продаж в память. Трекинг выключен везде: приложение ничего не пишет, кроме seed.

Raw SQL и Dapper не используются — всё выполняется через EF Core.

### Индексы

| Индекс | Зачем |
|---|---|
| `ix_sales_sale_date_status` | каждый запрос дашборда начинается с «продажи за период в нужных статусах» |
| `ix_sales_manager_id_sale_date` | рейтинг менеджеров и разрез по конкретному менеджеру за период |
| `ix_sale_items_sale_id` | join позиций к продажам — основа всех денежных агрегатов |
| `ix_sale_items_product_id` | группировка по товару для топа продуктов |
| `ix_products_category_id` | разрез «продажи и прибыль по категориям» |
| `ix_sales_customer_id` | подтягивание клиента в таблицу последних продаж |

Уникальные индексы на `products.sku`, `sales.number` и `categories.name` — защита от дублей в seed
и осмысленные ключи для ручных проверок в psql.

### Типы данных

Деньги — `numeric(18,2)`, не `double`: округление в аналитике должно быть предсказуемым.
Дата продажи — `date`, без времени: аналитика работает по дням, а время суток в задаче не участвует.
Цена и себестоимость дублируются в позиции продажи, потому что изменение прайса задним числом
не должно переписывать историческую маржу.

### Seed

Детерминированный генератор (`Random(20260901)`): пересоздание базы даёт тот же набор данных.
20 менеджеров, 80 клиентов, 6 категорий, 39 товаров, 3501 продажа за 12 месяцев.
Неравномерность заложена явно: сильные и слабые менеджеры, разный средний чек и скидочная политика,
сезонность с пиком в ноябре-декабре и провалом в январе, будни против выходных, отпуска и простои,
недавно нанятый менеджер, уволенный без продаж за последние полтора месяца, отмены и возвраты
чаще у отстающих, редкие убыточные сделки и одна намеренно огромная продажа.

Даты привязаны к дню первого запуска, чтобы пресеты «Сегодня» и «7 дней» не были пустыми;
`Seed:AnchorDate` позволяет зафиксировать конец истории явно.

### Frontend

React 19 + TypeScript на Vite 7, TanStack Query, Recharts, Motion.
Стили — CSS-модули рядом с компонентом (`Card.tsx` + `card.module.css` + `index.ts`),
токены в `styles/variables.css`, размеры в `rem`. Тексты интерфейса собраны в `locales/ru.ts`.
Блоки страницы лежат в `widgets/`, переиспользуемые элементы — в `components/ui/`.
Состояние периода живёт в контексте и целиком попадает в ключ кэша запросов —
поэтому смена периода автоматически перезапрашивает все блоки дашборда.

`keepPreviousData` во всех запросах: при смене периода старые цифры остаются на экране
и плавно пересчитываются, а скелетоны показываются только на первой загрузке.
Счётчики KPI анимируются, но уважают `prefers-reduced-motion`.

Разрезы «Сравнение менеджеров» и «Качество сделок» построены на данных, которые уже
приходят для рейтинга и KPI, — дополнительных запросов к серверу они не делают.

### Тесты

```bash
dotnet test backend/DJI.Market.slnx   # 46 тестов
cd frontend && npm test               # 14 тестов
```

Backend: формулы KPI и границы периода (чистые функции), пресеты периода на фиксированном
`TimeProvider`, ранжирование с ничьими, и сервисы аналитики на базе в памяти —
обработка статусов, счёт продаж, а не позиций, сравнение с прошлым периодом, спарклайны.
Провайдер InMemory не проверяет трансляцию в SQL: это осознанный размен, а корректность
запросов я проверял на живом Postgres, сверяя ответы API с прямыми SQL-запросами.

Frontend: скелетоны на первой загрузке, состояние ошибки с кнопкой повтора, пустой период,
смена пресета и произвольного диапазона (включая отказ применить перевёрнутый диапазон),
переключение режима рейтинга с проверкой, что пересортировка уходит на сервер.

## Что не успел за 8 часов

- **Кэш агрегатов.** Каждый запрос дашборда идёт в базу. На этих объёмах это единицы
  миллисекунд, но в production я бы закэшировал KPI и рейтинг по ключу периода.
- **Фильтр по менеджеру и категории на всей странице.** Бэкенд их принимает в таблице продаж,
  но глобального фильтра в UI нет — есть только период и статус.
- **Пагинация и сортировка в таблице последних продаж по клику на заголовок.**
- **Интеграционные тесты на живом Postgres** (Testcontainers). Сейчас сервисы протестированы
  на InMemory, а SQL проверялся вручную.
- **Мобильная вёрстка** — по условию не требовалась, и я её не делал.

## Что улучшил бы дальше в production

- **Материализованные представления** под тяжёлые разрезы, если период вырастет до нескольких лет.
- **Курсорная пагинация** вместо `OFFSET` в ленте продаж: на глубоких страницах `OFFSET` деградирует.
- **Разделение бандла**: сейчас 775 kB (237 kB gzip), из них большая часть — Recharts.
  Оба графика видны сразу, поэтому ленивая загрузка ничего не дала бы на первом экране,
  но при росте числа виджетов это первое, что стоит сделать.
- **Партиционирование `sales` по дате** и агрегатные таблицы по дням — когда продаж станут миллионы.
- **Метрики и трассировка** (OpenTelemetry) вместо чтения логов EF глазами.
- **CI**: сборка, тесты и прогон `docker compose up` на каждый PR.
